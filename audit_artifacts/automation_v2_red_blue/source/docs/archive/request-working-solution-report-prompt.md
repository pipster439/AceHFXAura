# Prompt：整理一份可验证的实现方案说明文档

## 背景

之前收到过两份自动化生成的"验证报告"，事后都被发现和实测结果不符：第一份报告了
一个实际没有发生的成功（脚本调用全部返回成功，但键盘灯效根本没变）；第二份用一套
没法独立核实的反编译/内核驱动叙事，掩盖了"测试程序没有打包身份"这种更平常、后来
被证明更接近真相的原因，而且报告里还有内部数字对不上的错误。

现在灯效控制问题应该已经解决了，需要出一份文档，但这次要求是**可验证**，不是
**叙事完整**。这份文档接下来会交给另一方（不是你）做独立核对，所以务必按下面的
要求来写，不要为了让报告看起来完整就把不确定的地方也写成确定结论。

## 硬性要求

1. **明确说清楚最终用的是哪个具体技术方案**：具体的接口名/CLSID 或 ProgID/协议
   细节（比如 HID 报文格式或者 WinRT LampArray 的具体调用），不要用"某种方式"
   "通过合适的接口"这类模糊表述。

2. **每一条结论都要标注是怎么确认的，区分"亲眼验证过的事实"和"推测/理论"**：
   - 如果是亲眼看到键盘物理变色，写清楚是谁看到的、什么时候
   - 如果是通过 Process Monitor 或类似工具观测到的，要附实际抓到的条目（进程名、
     操作类型、访问路径），不要只写"确认是通过 XX 服务实现的"这种总结性结论
   - 凡是没有直接证据支撑、只是根据现象推断出来的解释，必须明确标注为"推测"，
     不能和已验证事实混在一起写

3. **附上关键证据原文，不要只写结论**：
   - Process Monitor 或其他抓包工具的关键事件原始记录（截图或导出条目）
   - 最终生效的关键代码片段，必须是实际跑过的真实代码，不能是伪代码或者简化过的
     示意代码
   - 实际运行时的日志/控制台输出，包含时间戳

4. **说明排查过程中排除过哪些路径、为什么排除**，并且要对照现有 AGENT.md 里已经
   记录的排除记录做交叉核对——如果这次的新发现推翻了之前的某个判断（比如之前以为
   `aura.sdk.1` 完全不可行，结果发现是别的原因），要明确指出具体推翻了哪一条。

5. **诚实列出还不确定/没有完全搞清楚的地方**，包括这个方案有没有已知的局限性
   （比如是否需要特定权限、特定打包方式、是否在设备重新插拔后需要重新初始化等）。

## 输出文件

生成一份 Markdown 文件，命名为 `WORKING_SOLUTION_REPORT.md`，建议结构：

```
# 最终方案概述
一段话说清楚用的是什么技术方案

# 关键技术细节
接口名/CLSID/协议细节 + 实际跑通的代码

# 验证过程与证据（按时间顺序）
每一步做了什么、观察到什么、证据是什么（截图/日志/物理观察），
明确区分"看到的事实"和"由此推断的原因"

# 与既有排查记录的对照
对照 AGENT.md 里已经记录的排除路径，说明哪些结论被推翻了、哪些被证实了

# 已知限制与待确认事项
包括任何权限/打包/设备热插拔相关的注意事项
```

写完之后不要自己下结论说"已完全解决"，客观呈现证据，结论留给交叉核对之后再定。
